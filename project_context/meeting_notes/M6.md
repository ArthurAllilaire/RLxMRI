## Water Cache work

How it works: (water_cache.jl for code)

The core factorisation

The MRI simulator (KomaMRI) is linear in spins — so the full k-space is exactly:

S_full = S_spheres + S_water

Water is one homogeneous material, so its k-space row k (acquired on shot k) factorises:

S_water[k, :] = Mz_shot[k](TI, TR, α) · sin(α) · W_α[k, :]

- Mz_shot[k] — the longitudinal magnetisation at excitation time for shot k. Depends only on T1_water, TI, TR, α, and the shot index k. Fully
analytic (from transient_mz_at_excite_npe).
- W_α[k, :] — the geometric template: spin positions → Fourier encoding, T2 echo decay at TE_ref, any static B0 phase. This is what you get
when you divide out the Mz · sin(α) factor from a real Bloch simulation.

Why TI and TR scale for free

Once you have the template W_α at a reference TI/TR, evaluating at a new TI/TR is just:

1. Recompute Mz_shot[k] analytically for the new TI/TR — O(Npe) arithmetic.
2. Multiply each row by its own scalar: W_α[k,:] × Mz_shot[k](new TI/TR) × sin(α).

## Increasing voxel size of water

Above caching, when running the full sim having fewer water spins could be also be a good middle ground. This allows B0 inhomogenity and interactions between particles/gibbs ringing etc. more realistic. So updated the build phantom code to have a seperate water_voxel_mm. However, this changes the grid that is used to voxelise the sphere and so taking slices of 1mm thickness would sometimes not get any water particles. Instead, generalised the design:

1. Generalised slice from z-axis only to any plane: specified using a centre point and normal vector.

Note: the centre point is used as the origin for the grid of that plane (i.e. each point will be centre + i*voxel_dx)

2. Within each plane water is at water_voxel_size_mm apart - we correct for the fewer spins by scaling $\rho$ using a water weighting constant.

3. For slice thickness we then stack many planes water_throughplane_voxel_size_mm apart.
Note: tradeoff between realism and spin count - for lower spin count increase slice thickness (water_throughplane_voxel_size_mm) and the $\rho$ will be scaled to make up for the fewer spins (as k-space signal is sum of spins).

4. Have kept the implementation memory efficient (when using a plane or slicing a sphere) spins are pre-filtered by axis bounds to avoid wasting initialisation.

5. For full 3d similar layout as before - just water grid coarser.

Overall quite tricky to get right but full sim with 3mm water and 1mm sphere voxel = **6,919 spins** compared to **23,735 spins** with 1mm water (71% reduction; 2mm water = 9,565 spins). Water-only spins drop from 18,919 → 2,103 (89% reduction). Sphere-only (no water) baseline = 4,816 spins. (T15 field, 64×32, 1mm sphere voxel, default FOV=0.2m, slice.)

Notes: The per-shot transient Mz[k] doesn't analytically rescale across α. For a 90° pulse, cos(α) = 0 so each shot starts from the same thermal state — the transient ramp is flat. For α=30°, residual magnetisation carries over between shots, building a row-by-row amplitude gradient. The ratio of Koma's actual per-shot transient to the analytic model goes from 1.01 on row 1 to 1.40 on row 16 at α=30° vs α=90°. So you can't just rescale Mz_shot with a different α — the analytic model itself has α-dependent error.

The geometric template W_α itself changes with α. The template is extracted from a real Bloch simulation, so it captures how α affects spoiling, magnetisation evolution, and echo formation. This introduces 7–21% spatial variation between a 30° and a 90° template. Using the wrong template means every pixel in the water image is systematically wrong — and the error doesn't depend on TI (so TI-rescaling won't save you).
